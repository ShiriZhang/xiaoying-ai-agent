# 复盘与改进

项目完成了从问题、检索、原文读取到有引用回答的单Agent链路。最难的问题是：结构合法、引用存在和测试通过，仍不足以说明模型行为符合业务要求。真实运行暴露出的冲突处理与记忆问题，比增加框架或界面更值得优先解决。

## 最难的问题：证据正确与行为正确并不相同

早期真实运行出现过裸引用标记、多重追问、补查后未读取新候选，以及在期限冲突时建议“临时按更严格15天”。有些输出状态与引用来源合法，业务解释却不可靠。修复明确了引用格式、具体反馈、只回答所问及冲突不可擅裁的边界，并用真实样本重新检查动作和答案，而非只检查status。

另一个问题是对话锚点保存了“15天与30天规定冲突”。它有合法字段和消息来源，却把旧企业结论带入后续上下文。修复同时覆盖新快照与旧数据库快照；业务合法而记忆非法时保留答案、停用锚点，不新增模型调用。

有限内容检查也出现过误判：“报销所需提交材料”被拒；“待确认适用制度：15天与30天规定冲突”又能借议题前缀绕过。增加正例、分句和拼接反例后，重新运行了40轮真实回归。原失败、修复说明和后续结果见[效果验证](03-evaluation.md)。

## 个人学习收获

我参与了Agent架构、loop和记忆设计的讨论。这次锚点问题让我从“有一个记忆模块”的概念，进一步理解了记忆应保存什么：可以记住对象、关注事项和待确认问题；具体期限与产品能力仍要从本轮原文获得。

我也认识到结构校验、来源校验和语义符合性属于不同层次。字段完整、消息来源合法，并不能保证内容适合作为记忆。只限制新生成结果还不够，旧快照再次进入模型前也要检查。

我要求使用“冲突问答→修改资料→显式重载→同会话追问”的验证。AI实际将隔离资料改为45天并明确替代关系，再检查模型是否读取新原文、更新引用和清空待澄清项。这帮助我把“记忆理解对象、事实重新查证”的原则转化为可观察的动作与证据。

我还理解到修复需要同时检验误判和绕过，不能简单屏蔽数字，也不能只针对一个失败句子。代码、测试和真实运行由AI执行；我的参与集中在问题理解、约束和设计决策，分工见[AI辅助记录](04-ai-usage.md)。

## 取舍与投入

原生循环让工具选择、计数和停止原因直接可查；本地小规模索引减少部署成本；SQLite满足单进程演示的持久化需求。没有为展示框架而增加多Agent、向量数据库或生产Runtime。

原计划18小时，其中6小时用于验证、修复和材料。个人阶段性投入自述约12小时，不能从程序耗时推算剩余个人工时。真实模型预算为30元；已知用量采用保守费率估算，服务失败含未知usage，项目总费用与实际账单尚未完成核对。

## 已知限制与下一步

- 固定40轮与每类两次不能证明泛化稳定性，下一步扩充同义表达、复合问题和冲突措辞并观察重复运行差异。
- 引用回填只保证来源，仍需评估答案是否受原文支持；优先加入更丰富的语义失败样本。
- 锚点有限规则可能漏判或误判，继续覆盖合法关注事项与隐含旧结论，保持记忆失败不损伤合法业务结果。
- 材料回答偶尔附带有依据的审批流程，可进一步收紧输出范围并做受影响场景回归。
- 只实测Windows/CPython3.12和本机单进程。Reranker、检索对照实验、权限和线上部署未实现，不将这些可选扩展描述为已完成。
