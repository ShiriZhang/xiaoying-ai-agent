# reproducible-evaluation

## Purpose

使评审能从仓库在声明环境重现流程与真实效果，并区分设计预期、模拟流程、实际向量检索和真实模型决策。通过实际输入输出、失败复跑和全新环境记录证明项目，而不是以截图、预填日志或全局依赖替代交付。

## Requirements

### Requirement: 三层验证边界清楚
项目 SHALL 提供可执行的离线流程测试、真实 embedding 检索验证和真实模型端到端验证，分别说明能证明什么。条件缺失 SHALL 标为未运行或未完成，不能以 Mock 或跳过结果声称真实层通过。

#### Scenario: 离线层成功
- **WHEN** 无密钥与权重条件下运行模拟决策和模拟编码的测试
- **THEN** 测试只声明工程流程覆盖，不据此报告真实语义召回或模型决策效果

#### Scenario: 真实检索层
- **WHEN** 使用真实本地权重而不调用生成模型
- **THEN** 记录支持片段、自然改写与冲突双侧的候选召回及参数，不把检索结果等同于最终回答正确性

### Requirement: 六类真实场景独立重复运行
项目 SHALL 使用真实生成模型与真实混合检索，将明确答案、文档冲突、资料外问题、自然改写、上下文追问、工具失败六类核心场景各独立运行两次，保存实际结果。工具失败 SHALL 由真实业务工具故障注入产生，而不是把真实模型换成脚本。

#### Scenario: 核心验收材料完整
- **WHEN** 审阅 examples/ 的核心运行清单
- **THEN** 能找到六类场景的两次独立记录；资料外包含住房补贴缺口与天气，追问包含完整两轮请求，失败场景保留真实模型收到错误后的动作

#### Scenario: 至少两种动态路径
- **WHEN** 比较充分依据、冲突或故障场景的真实 Trace
- **THEN** 至少两条路径体现不同观察导致后续动作不同，并保留实际查询调整记录，不要求固定措辞或完全相同动作顺序

### Requirement: 关键业务边界与变更回归
项目 SHALL 验证仅 D01 可答、加入 D02 后冲突、有效替代、未来生效、部分回答、上限、模型不可用及记忆失败。候选人或独立AI审查代理 SHALL 提出至少一次资料修改，先说明预期，再核查重载后的真实回答、引用与动作。AI审查代理须独立于主要实现者；贡献和核查执行者须如实记录，AI操作不得记为候选人亲自完成，代理时间不得计入个人工时，未核实账单不得记为已核实。

#### Scenario: 人事新旧规则
- **WHEN** 使用提前 2 个工作日旧规则与提前 1 个工作日且明示替代的新规则，并冻结任务日期
- **THEN** 验证已生效与尚未生效两种结果，引用支持判断，不能只测试较新日期排序

#### Scenario: 资料变更驱动行为
- **WHEN** 从单 D01 变为 D01/D02 冲突，或替换产品原文后重建索引
- **THEN** 保存变更前后资料指纹、预期和实际结果，核查答案、引用及是否补查/停止随观察改变，不用硬编码数字通过测试

#### Scenario: 失败边界独立检查
- **WHEN** 测试工具恢复、格式修正、两种调用上限、超时或记忆失败
- **THEN** 分别验证计数、未完成与锚点停用规则，不只运行一条正常路径

#### Scenario: 冲突问答后资料更新的同会话追问
- **WHEN** 同一会话先完成真实期限冲突问答，随后在隔离资料副本中明确消除冲突、显式重载，再提交“那现在应该按哪个？”等上下文追问
- **THEN** 系统仍能理解讨论对象，但重新检索和读取当前资料；答案及引用依据新快照，不沿用旧冲突结论；新生成及实际传入模型的锚点均符合内容边界

此场景 SHALL 在运行前记录资料修改、明确替代关系与生效条件、预期结果，不得仅按日期或暗设优先级消除冲突。第一轮 SHALL 读取冲突双方、补查并说明未消解冲突；修改后 SHALL 显式重载并保留同会话原始历史，再检查第二轮实际模型输入、检索读取、新引用及回答。正常新会话产生锚点的链路，以及载入已确认污染旧锚点的路径 SHALL 分别验证，不能仅验证新快照生成。

证据 SHALL 包含运行前预期、两轮完整结果与Trace、前后资料快照及指纹、锚点前后状态、实际传入模型的锚点与历史选取记录、模型和向量配置、usage及源码版本。原失败、旧版本报告和每次修复后运行 SHALL 分开保留，不覆盖或事后改写。真实模型、权重、预算或运行条件不具备，以及任一关键检查失败时，本场景保持未完成，不能以Mock、结构校验或旧版本通过结果替代。

### Requirement: 实际证据与失败记录
项目 SHALL 在 examples/ 保存实际输入、输出、Trace 和测试结果，至少覆盖正常、资料不足、工具失败三组及全部验收点；评估文档逐项引用。失败、修复和复跑 SHALL 如实保留，未通过项列为限制，不能用预期冒充实际或挑选成功宣称整体通过。

#### Scenario: 失败后复跑
- **WHEN** 某真实用例失败，修复后再次运行
- **THEN** 原失败、修改说明、复跑结果与对应配置均可查，两次小样本不被宣称为统计稳定性或泛化证明

#### Scenario: 证据版本可核查
- **WHEN** 查看输出和 Trace
- **THEN** 能关联资料指纹、模式、模型标识、日期时区、依赖环境与代码版本信息，不提交真实密钥或隐私数据

### Requirement: 完整交付文档与配置声明
仓库 SHALL 包含 README、src/、tests/、examples/、data/、docs/01–05、依赖声明和 .env.example。README SHALL 提供环境、安装、启动、真实/Mock 请求和评审导航；五份文档分别说明需求、方案、实际评估、AI 使用和真实复盘，标明版本、职责、未完成项及个人贡献。

#### Scenario: 评审按入口操作
- **WHEN** 评审从 README 开始
- **THEN** 能找到离线和真实模式的完整步骤、模型权重准备、四个 API 的请求方式、测试与证据入口，不以截图或视频替代代码

#### Scenario: 环境变量示例可安全复用
- **WHEN** 复制 .env.example 并按说明配置
- **THEN** 所有必需和可选变量、模式、模型/本地权重位置与预算参数有说明，真实密钥不在仓库，Mock 不要求真实密钥

### Requirement: 全新环境可复现验证
项目 SHALL 在不继承全局包的全新环境或干净检出中，仅按声明依赖和 README 步骤安装、启动、测试并调用 API，保存环境版本、命令、结果及限制。Mock 运行 SHALL 在无真实密钥、无权重缓存时不联网；真实层 SHALL 通过显式权重准备与配置另行验证，不能依赖开发者隐式缓存。

#### Scenario: 冷启动 Mock 复现
- **WHEN** 在干净环境安装声明依赖后，以空模型缓存和无密钥启动 Mock
- **THEN** 四个 API 与离线流程测试可运行，记录安装与运行步骤，运行阶段没有权重下载或外部请求

#### Scenario: 真实层独立准备
- **WHEN** 按 README 获取并指定真实权重及模型配置
- **THEN** 记录准备过程、模型/依赖版本及真实检索和端到端运行；下载或服务失败明确标为未完成，不用旧缓存或模拟结果替代

### Requirement: 可读仓库与诚实提交信息
项目 SHALL 以同一 GitHub 仓库交付题号、URL 和最终 commit SHA，确保指定评审可读取。实际工时、费用、AI 辅助及个人工作 SHALL 按发生记录；Reranker 与对照实验为可选项，不能替代必交能力或挤占验证材料。

#### Scenario: 提交前核查
- **WHEN** 准备最终交付
- **THEN** 确认 GitHub 目标、最终 SHA、评审访问性、无密钥与证据完整性；私有仓库核实指定评审账号，不猜测账号或默认公开仓库

#### Scenario: 尚未完成真实验证
- **WHEN** 因模型、权重或预算条件尚未取得真实记录
- **THEN** 文档如实写未完成并说明限制，不将规划校验或离线通过描述成真实验收通过
